// why litebox

A small surface, by construction.

LiteBox puts a library OS between programs and the host. Guests keep the interface they expect; the host sees only the little that LiteBox needs.

Minimal host interface

The library OS answers guest syscalls itself, so the host is reached through a drastically smaller interface.

North shims, South platforms

A Rust-y, nix/rustix-inspired North interface over a pluggable South platform connects any shim to any platform.

A broker holds the authority

Files, sockets, and processes are brokered: a broker process owns them and enforces policy and quotas on every one.

Unmodified programs

Run Linux binaries as they are. This page's server is the stock busybox image, forking and exec'ing as usual.

Works with containers

A containerd shim runs each container in its own broker: docker run --runtime io.containerd.litebox.v1.

Exposure is opt-in

Guests reach only what policy allows, and are reachable only on ports the operator publishes, on loopback by default.

// architecture

Any North, any South.

LiteBox is designed for both kernel and non-kernel scenarios: the same core connects guest-facing shims to whatever the program runs on.

// run it yourself

One script to this page.

With the LiteBox containerd shim installed, Docker runs any image in a LiteBox broker. Guests use the host's network through the broker, so ports are published with an annotation rather than -p.

litebox/website 
# serve website/public from busybox httpd, inside LiteBox
$ ./website/serve.sh
# which runs
$ docker run -d --name litebox-site --runtime io.containerd.litebox.v1 \
    --network host \
    --annotation io.litebox.publish.tcp=127.0.0.1:18080:80 \
    -v "$PWD/website/public":/www busybox sh -c \
    'echo "*.sh:/bin/sh" > /tmp/httpd.conf && exec httpd -f -p 80 -h /www -c /tmp/httpd.conf'
